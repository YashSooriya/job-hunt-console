# Implementation Contracts

Status: active implementation contract through Milestone 25.

## 1. Architecture

```text
Browser
  -> Next.js web application
      -> server-side domain services
          -> PostgreSQL / Supabase
          -> Supabase Storage
          -> deterministic job-intelligence package
          -> Google APIs
      -> background worker
```

ChatGPT Plus is the preferred higher-quality reasoning surface for interactive job analysis, tailoring and application review. The V1 web app must not require separately billed OpenAI API usage.

V1 uses a single web application and a worker, not microservices.

## 2. Technology choices

- Next.js 16.x / TypeScript on Node.js 22+
- PostgreSQL hosted by Supabase
- Supabase Auth with Google OAuth
- Supabase Storage for canonical application documents
- deterministic evidence-grounded job analysis for zero-cost first-pass triage
- ChatGPT Plus for higher-quality interactive reasoning without separately billed API usage
- strict JSON Schema for machine-readable AI operations and ChatGPT handoff/import contracts
- deterministic structured-CV engine plus LaTeX/PDF renderer
- Cloudflare Workers/OpenNext for the hosted Next.js application

The production dependency lock file, not this document, will be the source of truth for patch versions. Next.js security patches must be applied before public deployment.

## 3. Domain identifiers

All persistent entities use UUID primary keys generated by PostgreSQL.

Externally sourced records also retain provider identifiers, source URLs, and source-row/message IDs for reconciliation.

## 4. Trust classifications

```text
verified       known candidate fact
proposed       generated/inferred answer requiring review
user_required  must remain unanswered until the user supplies it
```

## 5. AI contract rule

A model response used by application logic must validate against the corresponding schema in `packages/contracts/schemas/`.

Free-form prose may be displayed to a user but must not control state transitions, scoring arithmetic, permissions, or document approval.

## 6. Intelligence routing

The default web application must remain operable at £0 additional monthly cost.

- deterministic code performs first-pass requirement extraction, evidence matching, scoring arithmetic, CV-family selection and triage
- ChatGPT Plus performs higher-quality contextual reasoning when the user invokes ChatGPT from the workflow
- no web-app feature may silently depend on separately billed OpenAI API calls
- if API integration is introduced later, it must be optional and explicitly enabled

Model identifiers are never hard-coded business rules.

## 7. Evidence rule

Every material generated CV bullet must carry `evidence_ids: string[]` with at least one accepted evidence item.

The renderer and approval service must reject an application CV version that has a material generated claim with no accepted evidence link.

## 8. Scoring arithmetic

The deterministic engine or an approved ChatGPT analysis may propose component scores and explanations. Application code calculates weighted totals.

This prevents model arithmetic drift and enables reweighting without regenerating all analyses.

## 9. Application transition service

All primary state mutations must flow through one domain service / database function.

The database migration creates a transition table and `transition_application_state()` function. Direct writes to `applications.state` should be prohibited from ordinary application code.

## 10. Immutability

When `document_versions.submission_locked_at` is non-null:

- structured content cannot change
- rendered object key cannot change
- LaTeX source cannot change
- evidence links cannot be removed

Corrections create a new version.

## 11. Background jobs

Initial task types:

- `analyse_job`
- `prepare_application`
- `extract_candidate_evidence`
- `generate_cv`
- `generate_cover_letter`
- `prepare_screening_answers`
- `render_document`
- `sync_tracker`
- `classify_email`

Each task must have a deterministic idempotency key.

## 12. External provider boundaries

### Google Sheet

- import historical rows
- mirror application changes after cutover
- never use the Sheet as the authoritative state store after migration

### Gmail

- read-only in V1
- provider message IDs are retained
- uncertain classification does not mutate application state
- Google OAuth requests `https://www.googleapis.com/auth/gmail.readonly` and the narrow `https://www.googleapis.com/auth/drive.file` scope for the optional managed tracker Sheet
- deterministic email classification/matching is the default zero-cost path
- auto state changes require classification + Application-match confidence thresholds
- offers and recruiter messages are always user-reviewed
- provider message IDs make ingestion idempotent
- Google access/refresh tokens are not persisted in public application data tables; refresh tokens are stored encrypted in Supabase Vault through user-scoped RPCs
- the user chooses a per-profile monitoring cadence; dashboard sync runs only when due, and the user-created ChatGPT Task should use the same cadence
- ChatGPT assigns categories through token-bound MCP tools; only offers, recruiter follow-ups, uncertain classifications and ambiguous matches remain human review points

### Managed Google Sheets tracker

- `candidate_automation_settings` stores the per-profile cadence and optional managed Sheet workbook/tab metadata
- the app can create a tracker with Google Sheets API or connect an existing workbook explicitly selected through Google Picker; `drive.file` does not become broad Drive access
- the writer clears and rewrites only the recorded managed tab (creating it when necessary) and never falls back to another tab or workbook
- PostgreSQL remains authoritative; the Sheet is a user-visible mirror of application statuses
- ChatGPT may synchronize only the Sheet recorded for the connected member, and every sync is audit logged

### External ATS / employer forms

- no ATS passwords or employer credentials are stored
- the Milestone 10 browser helper uses a user-controlled local Chrome session via CDP
- the core observer/planner/executor is website-agnostic and does not choose a provider workflow
- every action is followed by re-observation before another action
- authentication, MFA, CAPTCHAs, unknown required fields and user-only declarations pause
- final submission is blocked until application-specific Approval Gate 2

## 13. API/server action principles

- authenticated user identity is resolved server-side
- every user-owned query is scoped by user ID
- client cannot provide an arbitrary owner ID
- consequential mutations produce audit events in the same transaction when possible
- model output is validated before persistence

## Milestone 4 application-creation contract

Application creation is transactional and idempotent through `public.create_application_from_job(job_id, origin)`.

New Applications freeze `job_snapshot_id` and `job_analysis_id`, retain `selected_cv_family`, record `preparation_origin`, and begin in `preparing`. The database rejects `reject`/`ineligible` jobs and independently re-checks the `auto_prepare` gate rather than trusting the browser.

The creation RPC is `SECURITY INVOKER`; RLS remains authoritative. It also creates the strategy/evidence link and idempotent preparation tasks. Content tasks are tagged `chatgpt_plus_handoff` so the default architecture does not require paid OpenAI API usage.

## Milestone 5 CV/document contract

The default application CV engine is `deterministic_v1` and must remain usable without separately billed OpenAI API calls. It may select, condense and reorder verified base-CV material. It may not invent a new material claim.

Canonical base CV content is stored as structured data in `data/cv/base-families.json`; rendering is downstream of content selection. Layout commands are never a tailoring input.

`public.create_cv_document_version()` is the canonical persistent write path for generated application CV versions. It is `SECURITY INVOKER`, checks application ownership and selected CV family, rejects non-empty `unsupported_claims`, and requires all persistent material evidence IDs to resolve to verified evidence owned by the candidate profile.

Each generated CV creates a new `document_versions` row. Existing versions are never overwritten. PDF files are private objects in the `application-documents` bucket. Submitted document content and its evidence links are immutable.

- CV persistence has a deferred evidence-manifest constraint: each material structured claim/evidence pair must exist in `document_evidence_links` by transaction commit.

## Milestone 6 application-content contract

`public.application_salary_contexts` stores one current salary context per Application. It records whether the source is `advertised` or `estimated`, the range/recommendation, currency, confidence, trust and the basis used.

`public.save_application_content_package()` is the canonical Milestone 6 write path. It is `SECURITY INVOKER` and therefore remains constrained by RLS. The RPC:

1. verifies authenticated Application ownership
2. upserts salary context
3. replaces only the milestone-generated screening package, leaving future ATS-specific answers separate
4. requires Green/`verified` answers to resolve to verified candidate facts
5. refuses values for Red/`user_required` answers
6. validates cover-letter evidence provenance when a letter is present
7. creates a new cover-letter `DocumentVersion` rather than overwriting an earlier version
8. updates preparation-task states and writes an audit event

The default content engine is `deterministic_v1`; ChatGPT revisions are later versions, not silent mutations.

## Milestone 7 review-centre contract

`public.application_review_packages` is the canonical record of the exact package selected for Gate 1. It pins `cv_version_id`, optional `cover_letter_version_id`, `cover_letter_decision`, assembly time and approval time.

The canonical RPCs are:

- `assemble_application_review_package(application_id)`
- `review_application_document(application_id, version_id, decision)`
- `review_application_salary(application_id, recommended_value)`
- `review_application_answer(application_id, answer_id, answer_text)`
- `set_application_cover_letter_decision(application_id, decision)`
- `approve_application_content(application_id)`

All are `SECURITY INVOKER` and operate under RLS. The generic `transition_application_state()` RPC explicitly refuses the reserved `ready_for_review` and `content_approved` target states so business logic cannot bypass either gate.

A generated salary change clears any stale approval. A newly generated CV or cover-letter version becomes the current review candidate while Gate 1 remains open. Gate 1 validation is repeated in PostgreSQL immediately before setting `content_approved`; UI checklist state is informative but never authoritative.


## Milestone 8 Gmail-monitoring contract

`public.process_application_email()` is the canonical persistence/action RPC. It is `SECURITY INVOKER`, runs under RLS, upserts by `(user_id, provider_message_id)`, preserves classification and match provenance, and may apply only the narrow deterministic post-submission state changes defined in the Gmail policy.

`public.resolve_application_email()` is the human override path for `Needs You` items. A manual decision sets the authoritative Application link and classification and may then apply the corresponding state transition.

`public.gmail_sync_state` records connection/sync health but never stores Google access or refresh tokens. `public.store_gmail_refresh_token()` and `public.get_gmail_refresh_token()` are SECURITY INVOKER wrappers around private, user-scoped Vault helpers. Refresh credentials are encrypted by Supabase Vault and used server-side only. `needs_reconnect` is an expected recoverable state when the credential is absent or revoked. Gmail remains read-only.

## Milestone 9 progression-preparation contract

`public.workflow_preparation_versions` stores immutable historical preparation versions for assessment and interview workspaces. Each version captures its own `context_snapshot`, `context_quality`, preparation payload and generator provenance.

`public.application_submission_contexts` is the immutable later-stage source of truth for the exact submitted application package. Milestone 10 must create this record at submission time; Milestone 9 reads it when present and otherwise labels reconstructed context as `approved_pre_submission` or `best_available`.

`public.save_progression_preparation()` is the canonical persistent write path. It is `SECURITY INVOKER`, checks ownership through the linked Application, requires `practice_only=true`, and rejects live-assessment answer/submission fields. Assessment preparation is preparation only; it cannot be used as an assessment-answer or submission endpoint.

The default workspace generator remains `deterministic_v1`. ChatGPT Plus handoffs may deepen preparation without requiring a separately billed model API.


## Milestone 10 adaptive form-agent contract

`public.start_form_agent_session(application_id)` is the authenticated Gate 1 -> browser-session entrypoint. It requires an approved review package, creates a random 256-bit session credential, stores only its SHA-256 hash, expires it after eight hours, and moves the Application to `form_in_progress`.

The local companion is `@jobhunt/browser-agent`. It connects to user-controlled Chrome over the DevTools protocol using Playwright Core 1.62.1. It observes DOM/accessibility state, builds a validated `FormAgentPagePlan`, executes at most one safe action, and then re-observes. It never contains provider-specific Workday/Greenhouse/Lever workflows.

The narrow `form-agent-bridge` Supabase Edge Function uses custom session-token authentication. The token scopes access to one Form session/Application and is not an ATS credential. The function persists sanitized observations/plans and uses service-role-only RPCs for form-state transitions.

Final submission controls are not executable ordinary actions. On detection the session moves to `final_review` and persists a structured diff. `approve_form_agent_final_review(session_id)` is Approval Gate 2 and moves the exact session to `approved_for_submission`. Only then may the local helper click the reviewed final submission control. A changed/missing control requires re-review.

Successful helper submission or explicit `I submitted it myself` recording creates `application_submission_contexts`, locks the selected document versions, and moves the Application to `submitted`. The generic application transition RPC is prohibited from targeting browser-form states or `submitted`.

### Browser helper commissioning contract

- Pairing codes expire after ten minutes and are single-use.
- Device credentials are stored only as hashes in Supabase and as secrets in the local OS credential store.
- The local config file must not contain the raw device credential.
- A paired device can claim only form sessions explicitly bound to its device ID and user.
- Short-lived form-session credentials are not persisted in the local config and are not passed in daemon child-process command arguments.
- The macOS helper health listener binds to loopback only.
- Background user pauses are resumed through an authenticated web-app RPC; no interactive terminal is required.

## Milestone 15 ATS acceptance and launch-qualification contract

`public.ats_acceptance_runs` stores genuine paired-helper no-submit acceptance evidence. The row is tied to one `form_agent_sessions` row, `submit_clicked` is database-constrained to `false`, and successful evidence requires the session to have reached the exact persisted `final_review` state. Acceptance records are not satisfied by source-backed fixtures.

`start_form_agent_acceptance_session_for_device()` is the commissioning entrypoint. It reuses the approved Gate 1 package and paired-device boundary but marks the form session `acceptance_mode=true`. A database trigger prevents any acceptance session from transitioning to `approved_for_submission`, `submitting`, or `submitted` regardless of client or service code.

`record_form_agent_acceptance_result()` is service-role-only. On successful final-review evidence it records the immutable no-submit run, closes the acceptance session and restores the Application to `content_approved`.

`get_v1_launch_status()` combines live cutover state, paired-helper state and persisted live ATS coverage. The web route adds runtime hosting/data-mode state. The UI may only report `v1_operational=true` when the hosted runtime is non-local, Supabase production data mode is active, Google/Gmail cutover is complete, a helper is paired, and the required live ATS matrix has passed.


## Milestone 16 invite-only multi-user tenancy contract

A valid Supabase session is necessary but not sufficient. Protected application routes require an active Job Hunt Console membership returned by `get_my_membership`. Membership acceptance occurs before Gmail refresh-token storage, candidate-profile creation or historical bootstrap claim. Roles are `owner`, `admin` and `member`. The owner cannot be revoked through the normal administration path.

Historical bootstrap ownership is bound to the authenticated Google email. A newly invited member receives an empty candidate profile and cannot claim or read another member's staged historical data. Existing user-owned application, document, Gmail and form-agent tables continue to use per-user RLS rather than a shared tenancy bucket.

## Milestone 17 per-user onboarding and applicant-knowledge contract

Fresh invited members build their own applicant knowledge base. Education, employment, skills, projects, publications, source documents, CV-family choices, reusable answers and onboarding state all resolve through the authenticated user's `candidate_profiles` row. Every new M17 table has RLS based on `private.owns_profile(profile_id)`. Candidate source-document storage paths start with the authenticated user ID.

CV extraction is proposal-only. Extracted facts and evidence enter `needs_review` and cannot be treated as verified until the user explicitly verifies them. The extraction source and locator remain attached to the proposal. User-supplied work authorisation can be stored only as an explicit verified fact and is never inferred from CV content or another member.

`get_onboarding_readiness` is the database readiness gate. It requires verified history, skills, evidence, explicit work authorisation, at least one location preference, at least one enabled CV family and zero pending extracted facts/evidence before `complete_candidate_onboarding` may set the profile to ready.


## Milestone 18 automation isolation contracts

- `authenticated` cannot execute private automation functions that accept `p_user`; only fixed public wrappers are member-facing.
- Gmail Vault store/read paths require an active membership and derive the user from `auth.uid()`.
- browser-helper pairing and device authentication are service-only RPCs that reject revoked/non-member identities.
- helper polling constrains form sessions by `browser_device_id` and `user_id`.
- paired form sessions send device credentials on every bridge request in addition to the rotating form-session credential.
- membership revocation revokes browser devices and pairing codes, cancels live form sessions and rotates their token hashes without deleting applicant data or Gmail secrets.
- Gate 2 approval remains scoped to the exact owned form session and application.
- operational exit requires a real two-user isolation acceptance run.

## Milestone 19 authenticated ChatGPT app surface

The ChatGPT integration is a public HTTPS MCP Streamable HTTP endpoint protected by OAuth 2.1 authorization code plus PKCE S256. OAuth metadata advertises the MCP resource and authorization server; the authorization route requires an active member's consent, access tokens are short-lived and refresh tokens rotate, and raw bearer tokens are never stored. The MCP route returns only the authenticated user's data and the database boundary re-checks active membership for every tool call.

M19/M25 read tools include get_candidate_profile, get_detailed_candidate_profile, get_search_preferences, get_automation_settings, get_pending_email_classifications, get_pending_work, get_application_context, get_verified_evidence, get_reusable_answers and get_browser_agent_question_context. M19/M25 write tools include save_discovered_job, save_job_analysis, save_application_package, classify_email, sync_application_tracker, report_user_required_question, queue_application_for_review, save_reasoning_result, mark_work_item_complete and mark_work_item_failed. No tool approves Gate 1, approves Gate 2, promotes Amber/Red evidence, or submits an employer form.

ChatGPT work items and reasoning results are per-user, idempotent and audit logged. The web setup page documents the supported user-created ChatGPT Task path and clearly separates it from hosted server scheduling. Publication remains subject to the current ChatGPT app/developer-mode and submission policies.

## Milestone 20 guided activation

`candidate_source_documents` stores the original uploaded CV, previous application document, work sample or user-supplied description privately under an authenticated user path. The Worker parser supports PDF, DOCX, TXT, Markdown and RTF; the source endpoint accepts files and/or pasted text. Extraction diagnostics remain on the source row.

`candidate_extraction_proposals` is an RLS-protected, profile-owned Amber queue. Each proposal carries its source document, locator and proposed claim/structured fields. The review route can reject it or explicitly materialize it as a verified `evidence_item` plus a verified employment, education, skill, project or publication record; no extraction proposal silently becomes reusable profile data.

`get_onboarding_readiness()` is the M20 activation gate. In addition to verified profile evidence and direct personal answers, it checks complete search preferences, an extracted source document with no pending review, Gmail connectivity, ChatGPT connectivity, confirmed ChatGPT Memory setup and a paired browser helper. `complete_candidate_onboarding()` refuses to set `ready` until the complete checklist is true.

Job-search preferences are stored per candidate profile and include role families, target seniority, preferred/excluded industries, locations, commute, work modes, salary floor/target, sponsorship requirement, posting-age policy, fit and auto-prepare thresholds, search cadence and application automation preference.

The MCP `get_detailed_candidate_profile` read returns the authenticated user's verified structured profile, evidence, preferences, enabled CV families, non-sensitive reusable answers and source metadata for future job matching and CV editing.

ChatGPT Memory remains a ChatGPT-controlled setting. New users see a first-use reminder linking to ChatGPT Settings → Personalization. When a user confirms Memory is enabled, that confirmation is stored per profile; MCP instructions use relevant previous ChatGPT knowledge when available as contextual recall, while verified Job Hunt profile data remains authoritative.

## Milestone 21 recurring job discovery

- `job_search_sources`, `job_search_runs` and `job_search_run_jobs` are user-owned, RLS-protected tables; run and result-link writes happen through trusted database functions/triggers.
- A search run is bounded by its member's enabled source keys and `max_jobs`; a second active run is not created within the active-run window, and non-forced ChatGPT Tasks respect the member's cadence.
- ChatGPT receives search context through token-bound RPCs only. It can request a run and read bounded dedupe context, but it cannot select another user or write directly to run tables.
- New `chatgpt_mcp` jobs and their analyses attach to the current user's running search run. Run completion counters are taken from the worker result plus trusted link rows.
- Source configuration is per-member and never carries a caller-supplied `user_id` in the web API.

## Milestone 22 automatic application preparation

- `application_preparation_requests` is an owner-readable, trusted-write table keyed by the member, job and analysis idempotency key.
- Automatic preparation requires an active member, a frozen vacancy snapshot, an eligible `auto_prepare` analysis, fit and priority at or above the member threshold, a recommended CV family and verified evidence IDs.
- The member's `application_automation_preference=manual` blocks the ChatGPT path. Other preferences may prepare content, but never bypass review.
- The token-bound MCP function reuses an owned Application or creates one with frozen job/analysis context, queues idempotent preparation tasks and records the package/audit decision.
- The only automatic state is before Gate 1. No function in the M22 path approves content, starts a form session, approves Gate 2 or records employer submission.

## Milestone 23 browser-helper reasoning loop

- A trusted `needs_user` transition creates a per-user `browser_question` work item with only bounded session/pause metadata and the latest observation reference.
- `get_browser_agent_question_context` returns only the connected member's active/paused sessions and bounded proposals. `propose_browser_reasoning` stores an advisory proposal and explicitly returns `resumed=false` and `applied=false`.
- The web user may accept or reject a proposal through a current-user wrapper, but acceptance never changes form-session status. The existing Resume control remains a separate explicit action.
- The local helper receives proposals as advisory context for display only; its deterministic observation/action validator remains authoritative and its final submission path remains Gate 2-controlled.

## Milestone 24 reliability and operations

- `automation_rate_limits` is per-user and bucketed across MCP reads, MCP writes, search runs and browser reasoning. The MCP route consumes a window before dispatching a tool and returns a bounded retry time when the window is exhausted.
- `get_pending_work` is bounded. `recover_stale_work` reclaims expired leased/running items and stops retrying after five attempts; it cannot recover another member's work.
- Settings exposes only operational counts and rate-window metadata through a current-user RPC. It does not expose private work payloads or credentials.
- Two-user production isolation, real ChatGPT OAuth consent and real helper pairing remain human acceptance checks. They must be recorded as pending rather than inferred from source tests.

## Milestone 25 email automation and managed tracker

- `candidate_automation_settings` is profile-owned and stores the email-monitoring cadence, next due time, optional managed Sheet identity and last-run health.
- Gmail ingestion remains read-only and bounded. The dashboard honours the stored cadence when opened; the ChatGPT Task prompt instructs the user to schedule the same cadence because the app cannot create a ChatGPT UI Task.
- `get_pending_email_classifications` returns bounded private messages plus application candidates. `classify_email` validates the token, ownership, enum category and confidence, persists provenance, applies only the existing safe status transitions and records a ChatGPT audit event.
- `sync_application_tracker` can create or update only the workbook and tab recorded for that member. It uses Google `drive.file`, clears and rewrites the selected tab mirror, and records sync health without making the Sheet authoritative.
